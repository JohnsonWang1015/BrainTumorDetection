# IDH Data Expansion Design

## Goal

Expand the current IDH training pool beyond the local `BraTS-TCGA-LGG` subset while preserving the existing 4-modality MRI pipeline and keeping source provenance explicit.

The immediate target datasets are:

- `TCGA-GBM`
- `UCSF-PDGM`
- `EGD`

The design objective is not to mix everything blindly. It is to define a manifest contract and cohort policy that let the repository answer three separate questions:

1. Does more data improve IDH performance on the current TCGA-style task?
2. Does more `IDH-wildtype` data improve class balance and threshold stability?
3. Do external cohorts help, or do they introduce enough shift that they should remain evaluation-only at first?

## Current State

The current pipeline is built around one manifest shape generated by `src/idh_glioma/data/prepare_dataset.py`:

- top-level splits: `train`, `val`, `test`
- per-record fields:
  - `case_id`
  - `date`
  - `modalities`
  - `mask_path`
  - `idh_label`

This is sufficient for a single-source BraTS-style cohort, but it is too weak for a multi-source molecular imaging workflow because it cannot answer:

- which dataset a case came from
- whether a case is preoperative or post-treatment
- whether a case has a segmentation-grade mask or classification-only data
- how the IDH label was joined
- whether a case belongs in training or should be treated as an external holdout

## Problem Statement

The repository currently has a small, imbalanced IDH cohort. That produces three coupled problems:

1. `IDH-wildtype` coverage is poor.
2. Validation and test metrics are high-variance because the labelled cohort is small.
3. The current manifest shape does not support controlled expansion into larger public cohorts.

If more data is added without a stronger contract, the codebase will blur together incompatible cases and the resulting metrics will be difficult to trust.

## Design Principles

### 1. Preserve current pipeline compatibility

The current training and evaluation code should continue to work through an adapter. A multi-source manifest should not force a full training-code rewrite before the first expansion experiment.

### 2. Separate cohort identity from split identity

`train / val / test` is not enough once multiple institutions enter the pool. We need cohort metadata that survives after splitting.

### 3. Encode eligibility explicitly

Not every public case is suitable for every task.

- Some records will be valid for 3D IDH classification but not segmentation.
- Some records will be useful only for external validation.
- Post-treatment cohorts should not silently contaminate the current preoperative task.

### 4. Make source-aware evaluation first-class

The manifest should support:

- pooled training
- source-held-out evaluation
- external-only evaluation

without creating separate ad hoc file formats.

## Recommended Expansion Order

### Phase A: TCGA completion

First expand within the TCGA family:

- complete `TCGA-LGG`
- add `TCGA-GBM`

This is the lowest-risk route because it is closest to the current repository assumptions and should help class balance by adding more `IDH-wildtype`.

### Phase B: UCSF-PDGM as external validation

Use `UCSF-PDGM` first as an external validation cohort rather than immediate training data. This isolates domain shift before the repository commits to mixed-source training.

### Phase C: EGD pooled expansion

After the repository can track cohort identity and source-specific exclusions, add `EGD` as the first large-scale mixed-source expansion.

## Manifest v2 Design

The new manifest should add a registry plus richer per-case records.

### Top level

The manifest should contain:

- `manifest_version`
- `created_at`
- `task`
- `cohorts`
- `splits`
- `split_strategy`

### Cohort registry

Each cohort entry should declare:

- `cohort_id`
- `source_dataset`
- `acquisition_stage`
- `intended_use`
- `source_url`

This allows the repository to represent:

- `tcga_lgg_only`
- `tcia_preop_pooled`
- `ucsf_pdgm_external`
- `tcia_plus_egd`

without inventing different file formats for each experiment.

### Per-case records

Each record should extend the current shape with:

- `record_id`
- `source_dataset`
- `source_subject_id`
- `cohort_id`
- `acquisition_stage`
- `mask_kind`
- `label_source`
- `label_confidence`
- `inclusion_flags`
- `qc_flags`
- `provenance`

The current fields should remain present:

- `case_id`
- `date`
- `modalities`
- `mask_path`
- `idh_label`

This is the compatibility bridge that lets the current code keep working.

## Cohort Policy

### Default training cohorts

The repository should formalize three main MRI/IDH cohort views:

1. `tcga_lgg_only`
   - direct continuation of the current baseline
2. `tcia_preop_pooled`
   - `TCGA-LGG + TCGA-GBM`
3. `tcia_plus_egd`
   - `TCGA-LGG + TCGA-GBM + EGD`

### Default external validation cohort

`UCSF-PDGM` should initially be evaluation-only.

### Excluded by default

Post-treatment cohorts should not be accepted into the default preoperative IDH pool unless explicitly requested.

## Task Eligibility Rules

### Segmentation

Keep only cases that have:

- all required modalities after alias normalization
- a usable tumor mask
- a cohort policy that allows segmentation training

### 3D IDH classification

Keep cases that have:

- all required modalities after alias normalization
- a valid `idh_label`
- preoperative eligibility by default

A segmentation mask is optional for classifier-only cases.

## Adapters

To reduce migration cost, the repository should add a compatibility adapter that converts a manifest v2 record into the current v1 training view:

- `case_id`
- `date`
- `modalities`
- `mask_path`
- `idh_label`

This adapter is the key to incremental rollout.

## Source-Specific Notes

### TCGA-GBM

- expected value: improve `IDH-wildtype` coverage
- likely first production-grade expansion target
- may contain classification-eligible cases without segmentation-grade masks

### UCSF-PDGM

- expected value: external validation and later mixed-source training
- should be tagged clearly so it can be excluded from the first pooled-train experiments

### EGD

- expected value: major volume expansion
- likely requires the most careful alias normalization and QC handling

## Validation Strategy

Each expansion stage should produce:

1. case counts by cohort
2. class counts by cohort
3. preop vs postop counts
4. segmentation-eligible vs classification-only counts
5. source-held-out evaluation where relevant

The repository should avoid reporting one pooled AUC without also reporting which cohorts were used for training and evaluation.

## Recommendation

The repository should treat this work as a data-contract migration, not a one-off import script.

The first implementation target should be:

1. multi-source manifest builder for `TCGA-LGG + TCGA-GBM`
2. adapter back into the current training manifest
3. source-aware reporting

Only after that should the repository wire in `UCSF-PDGM` and `EGD`.
